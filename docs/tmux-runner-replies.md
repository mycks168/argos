# tmuxの後続回答をRunnerで回収する

## 方式

Agent Runnerは1秒間隔で、このRunnerが所有するローカルtmuxスロットを確認する。
通常ターン・リセットと同じロックを取得し、フックの台帳にある未回収の親Stopと
既存の子回答ストアを、完了済みRunnerジョブへ取り込む。CLIを再実行しない。
リモートスロットは直接探索せず、相手側Runnerが回収する。

親回答は会話世代と台帳の行末位置、子回答は既存の識別子と本文から固定の回答IDを作る。
通常応答が引き取ったStopは個別の引取記録で除外する。
通常入力・未回収の手入力がある間は、その回答を横取りしない。
Codex・agyの起動確認中のStopは対象外とする。

ジョブのIDは回答IDそのものとし、スロット名・provider・会話世代を保持する。
回答ストアの予約中にジョブを保存し、保存後に転送マーカーを残す。
途中の保存失敗・Runner再起動では同じIDで再試行する。
転送マーカーにより、配信済みジョブの保存期限が過ぎても再登録しない。
回答・ジョブの保存ファイルは600、新規保存ディレクトリは700とする。

## 既存の配信経路

新規HTTP APIは追加しない。既存の未配信ジョブ一覧・claim・結果取得・配信済み通知を使う。
ARGOS本体の回収は既存の5秒間隔で、履歴保存が成功した後にRunnerへ配信済みを通知する。
ブラウザを閉じていても履歴・通知への反映は可能になる。

- ブラウザ起点: `background`ジョブとして履歴・通知へ反映する。音声は既存の
  `input_mode=background`とスロット別のブラウザ音声キューに残す。
- 本体PTT起点: `background_local`ジョブとして既存の本体音声待ちへ順番に追加する。
  この場合はブラウザ向け回答ストアを既読にして二重再生を避ける。

履歴IDは両経路とも`subagent-回答ID`で共通にし、後から同じ回答を取得しても重複表示しない。
別スロットでは未読扱いとし、本体音声はそのスロットに戻り、録音・再生が終わってから扱う。
親・子それぞれの接頭辞は共有関数で統一する。完了通知はブラウザでの実再生完了を意味しない。

## 導入・世代の扱いと制限

初回導入時は台帳の現在末尾を基準にする。由来が不明な導入前の回答を一斉に再生しないためで、
導入前の取りこぼしを自動復元する機能ではない。通常入力時にも送信前の基準位置を保存する。
会話リセット後は旧世代の回答を新しい会話へ挿入・再生しない。
旧世代ジョブは回収対象外として配信済みにし、元のフック台帳はこの処理では削除しない。

今回の耐久化対象は後続回答のRunner取り込みである。通常ターンのpending削除から
最終配信確認までの障害窓、実音声の厳密な一回再生は解消していない。
回答ストアの既読本文を含む512件上限・保持期限、孫の追跡、agyの複数DONEも別課題として残る。
配送先は同じ世代の直近入力元を引き継ぐ。子ごとの起動元追跡ではない。
同世代の古い親回答が新しい入力中に届く場合の意味的なターン同定も、完全保証ではない。

## 検証

合成テストは通常回答の除外、ターンロック、再起動、保存後の障害、同一IDの再試行、
ローカル向け配送、初回導入時の基準位置を確認する。

```bash
uv run pytest -q tests/test_tmux_reply_collection.py tests/test_background_delivery.py
ARGOS_TEST_REPLY_COLLECTION=1 uv run pytest -q -s tests/test_tmux_reply_collection_live.py --no-cov --tb=short
```

2026-10-18の隔離CLI試験は3件成功。Claude・agyでは子回答と自律再開した親回答が
各2ジョブになり、通常回答の重複登録はなかった。Codexでは子回答1ジョブを確認した。
Codexの親の自律再開は未観測であり、できないと断定する結果ではない。
試験は合成短文のみで、実スピーカー・マイク・ブラウザ実再生は検証対象外。
サービスへの反映にはRunnerとARGOS本体の再起動が必要で、この検証中には行っていない。

### 品質ゲート（変更範囲）

品質ゲートcheckに従い、回収ロジックを独立モジュールへ分離し、本体の定期監視も
一回分の回収へ分割してネストを減らした。抑制コメント・しきい値緩和は追加していない。

| 観点 | 結果 |
|---|---|
| 大きさ・複雑度 | 回収・配送の6ソースと追加3試験のRuff成功。9ファイルとも400行以下 |
| 型・依存 | 同9ファイルのstrict mypy成功。回収側はReplySink契約に依存し、core・画面層への逆依存なし |
| 重複 | 同9ファイルを50トークン・5行で検査し、重複0 |
| デッドコード | 全ソース・試験のvulture信頼度60で、新規指摘は試験のMock.side_effectのみ。実使用を確認 |

既存の`core/app.py`と`agent/runner.py`は400行超で、旧関数の複雑度・引数・型の違反が残る。
今回触れた監視処理のネスト違反は分割で解消したが、画面全体・既存HTTPハンドラの
再構成は対象外とした。strict mypyは上記9ファイルを対象とし、既存依存先はsilentで追跡した。
全体の型検査成功を意味しない。

全体のdeptryは262件。自己パッケージargosの誤認識と、既存の任意・間接依存などを含む。
新規内部importも同じ誤認識で増えているが、外部依存の追加はない。
依存定義・全体の既存違反はこの回収機能とは分けて扱い、品質ゲート全体合格とはしない。

検証結果: 全体1,212件成功・16件スキップ、行カバレッジ88.33%。
回収用の新規3モジュールは合成テストで行カバレッジ100%。
この全体実行後、本体監視の正常既読ケースも追加し、配送試験6件の成功を再確認した。
既存Bearer認証・claim・結果取得・配信済み通知で、取り込み回答の往復も確認した。
