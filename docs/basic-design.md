# 基本設計書

本書は常駐tmuxスロット拡張の設計。既存機能の外部仕様は `basic_design.md` を参照し、既存機能を書き換えるものではない。記載した追加機能は設計であり、実装済みを意味しない。

## 1. システム概要

- 1.1 目的・背景: CLI都度起動を残し、常駐するエージェントのターミナルを会話スロットで利用する。
- 1.2 システム全体像: ブラウザ → ARGOS → Runner → tmux → 対話型CLI。リモートは既存RemoteArgosClient → 接続先ARGOS → 接続先Runnerの順で処理する。
- 1.3 設計方針: 既存設定・会話API・音声処理を維持する。ターミナル描画と読み上げ本文の取得を分離する。仲介LLMは起動しない。
- 1.4 用語定義: 接続先ARGOSは既存のHTTP接続先。任意SSHホストへの直接起動とは区別する。

## 2. システム方式設計

- 2.1 ハードウェア構成: 既存ARGOSホストを使う。新たなGPUは要求しない。
- 2.2 ネットワーク構成: 入力と回答は既存HTTP/SSE経路を使う。ターミナル中継もARGOS認証下に置き、ttydを直接外部公開しない。SSHが必要な搬送方式を採用する場合もホスト鍵検証を維持する。
- 2.3 ソフトウェア構成: Python・既存HTTPサーバー・tmux・ブラウザターミナル。既存HTML/JavaScript構成を維持し、別のReactアプリやDBを導入しない。
- 2.4 環境構成: 専用ブランチで開発する。単体コマンドではなくARGOSから試すよう利用者が依頼したため、運用設定へ専用Claude試験スロットだけを追加する。この返信と実行中ジョブの完了を待って別プロセスから再起動し、認証付き会話APIと応答WAVを確認する。その他の設定・既存スロットは維持する。

## 3. アプリケーションアーキテクチャ

- 3.1 アーキテクチャ概要図: 会話入力 → 既存ターン処理 → 実行方式選択 → tmux入力。フック → スロット別イベント台帳 → 回答正規化 → 既存ターン出力・読み上げ。
- 3.2 レイヤー構成: 画面/APIは認証と入力検証、Runnerはジョブ管理、tmuxサービスはプロセス制御、台帳は永続化、イベントモデルはデータ定義を担当する。
- 3.3 モジュール分割: tmuxコマンド制御、CLI別起動引数、フック受信、回答正規化、ターミナル搬送を分離する。端末画面の文字列から回答を抽出しない。
- 3.4 共通部品: 既存AgentClient、create_provider_client、AgentJobStore、RemoteArgosClient、Bearer認証、音声ミュート経路を利用する。

## 4. 機能設計

- 4.1 機能一覧: REQ-025/026=実行方式と互換性、027=端末表示、028〜030=CLI対応、031〜033=音声会話、034=再接続、035=リモートARGOS、036〜038=分離・重複防止・障害表示。
- 4.2 機能詳細設計:
  - 実行方式は接続先ローカルスロットの `execution_mode: cli | tmux` で指定し、省略時はcli。既存 `type: local | remote` と混同しない。
  - スロットの内部キーはprovider・名前・作業ディレクトリを含む安定キーとする。tmux名はそのハッシュから生成し、利用者入力をtmuxターゲットやシェル構文として流用しない。
  - スロットごとに1つの所有セッションを作る。再利用時は所有キー・設定指紋・paneの生存を確認し、既存セッションへ無条件に入力しない。
  - tmuxコマンドは引数配列で実行し、コマンド処理にタイムアウトを付ける。入力文はシェルへ渡さず、tmuxバッファとして貼り付ける。ブラケットペーストと送信キーを分離する。
  - フックの生データはCLI別アダプター内で型付きイベントへ変換する。本文とツール進行を区別し、ツール出力を読み上げない。
  - Claudeの質問用ツール抑制、Codex・agyの通常文質問はCLIごとに実測する。抑制できない対話画面は入力待ちを表示し、自動承認しない。
  - 受信イベントはスロットキー、世代、CLIセッション、ターン/ステップ識別子で照合し、古い世代の完了を新しい会話に混ぜない。
  - ターミナルから直接送信されたターンも会話入力として追跡する。音声入力との同時送信は拒否し、入力を黙って破棄しない。
  - 最初の試作はローカル1スロット。表示・入力・音声・ブラウザ再接続の結合試験後に3CLIとリモートへ広げる。

## 5. 画面設計

- 5.1 画面一覧: 通常・SP・Gridの既存画面を使用する。
- 5.2 画面遷移図: 選択したスロットがtmux方式なら会話表示領域をターミナルに切り替え、従来方式へ戻すと既存会話表示へ戻る。
- 5.3 画面詳細設計: スロット名・状態・音声入力・共通ミュートを維持する。ターミナル入力フォーカス中のスペースはターミナルへ渡し、音声入力は明示的なPTT操作で開始する。ターミナル領域の実寸で列・行数を更新する。ブラウザ切断でCLIを停止しない。

## 6. データ設計

- 6.1 論理データモデル: スロット → tmuxセッション世代 → CLIセッション → ターン → イベント → 配信既読位置。
- 6.2 テーブル一覧: DB追加なし。セッション対応・フックイベント・既読位置を所有者専用の状態ファイルで保存する。
- 6.3 テーブル定義: 必須項目はslot_key、generation、session_name、pane_id、provider、CLIセッション識別子、event_id、event_kind、本文、取得時刻。CLI固有フィールドは正規化層内に留める。
- 6.4 マスタデータ設計: スロット設定はconfig.yaml。トークン・鍵はホームの.config配下で管理し、イベントへコピーしない。
- 6.5 データ量見積もり: 端末履歴・イベントログに上限を設ける。具体値は保存処理の実装時に根拠とともに記載し、未制限のまま運用投入しない。

## 7. バッチ・帳票設計

- 7.1 バッチ一覧: 専用帳票・定期バッチの追加なし。
- 7.2 バッチ詳細設計: フックはローカル記録のみとし、TTSやネットワーク応答を待たない。破損行は正常な完了にせずエラー記録する。
- 7.3 帳票一覧: 対象外。
- 7.4 帳票レイアウト概要: 対象外。

## 8. 外部インタフェース設計

- 8.1 インタフェース一覧: 既存Terminal API、Runner API、CLIフック、ターミナルの双方向搬送。
  - 8.2 API設計: 会話入力は既存POST /api/terminal/turnを維持する。端末搬送は認証付き/api/terminal/consoleでopen/input/resize/closeと読込位置付き長時間ポーリングを提供する。送信済みターンはinput_mode=observeで回収し、プロンプトを再送しない。経路・スキーマ・制限は[端末表示の仕様](tmux-console.md)を参照。閲覧認証のみでシェル入力を許可しない。
- 8.3 ファイル連携設計: フックイベントはUTF-8 JSONL。書込途中の行は次回読込まで保持する。初期CLI設定の信頼確認を検証し、共通設定へ無断でフックを追加しない。

## 9. 共通設計

- 9.1 認証・認可設計: 既存Bearer認証を必須とする。ブラウザ端末接続は短命な認証済み接続として扱い、長命トークンをURL・ログへ露出しない。接続のOriginも検証する。
- 9.2 ログ設計: 通常ログには本文・音声・認証値を記録せず、スロット内部IDとエラー種別を出す。
- 9.3 エラーハンドリング設計: 起動失敗・入力競合・フック欠落・CLI終了・通信切断を区別する。回答未取得を空回答成功として返さない。
- 9.4 国際化・多言語対応: エラー・説明・ドキュメントは日本語。

## 10. 非機能設計

- 10.1 性能設計: 端末サイズ変更をまとめて送信し、画面更新ごとにtmux起動を繰り返さない。回答はイベント差分で取得する。
- 10.2 可用性設計: ブラウザ切断・ARGOS再起動でtmuxを削除しない。プロセス再起動後の実行中ジョブ復旧は既存Runnerの中断扱いを踏まえ別途検証し、自動成功扱いにしない。
- 10.3 障害・監視設計: pane生存、フック受信、搬送接続を別々に監視する。Stopだけでバックグラウンド処理完了を断定しない。

## 11. セキュリティ設計

- 11.1 通信暗号化: 既存HTTPSを維持。外部向けの認証なしttydポートを作らない。
- 11.2 データ暗号化: 保存時暗号化の追加は対象外。状態ディレクトリ700、機微なファイル600を使用する。
- 11.3 脆弱性対策: shell=True禁止。利用者入力を起動コマンド、ターゲット名、ファイルパスへ展開しない。端末出力をHTMLとして挿入しない。
- 11.4 不正アクセス対策: 入力サイズ・列行数・接続数を制限し、任意tmuxセッションの参照を拒否する。
- 11.5 監査ログ: 端末操作の開始・終了と対象内部IDを記録し、コマンド本文は記録しない。

## 12. 移行設計

- 12.1 移行対象: 明示的にtmux方式へ変更した試験スロットのみ。
- 12.2 データ移行設計: 既存CLIセッションからの自動移行は行わない。
- 12.3 移行手順: 専用スロットを追加し、ローカル結合試験後に接続先ARGOSも更新する。
- 12.4 並行運用: 未設定は従来方式。試験失敗時は試験スロットを無効にし、既存スロットで継続する。
- 12.5 移行確認: 既存config.yamlと旧版クライアントからの会話を回帰試験する。

## 13. 運用・保守設計

- 13.1 起動・停止: 所有セッションだけを操作する。利用者の既存tmuxサーバーやセッションを一括停止しない。
- 13.2 定常監視: 画面の接続状態とCLI実行状態を区別して表示する。
- 13.3 バックアップ: 既存履歴とスロット対応・既読位置を対象とする。CLIプロセスのメモリをバックアップ可能とは扱わない。
- 13.4 更新: CLIバージョンとフック形式を記録し、変更時は契約テストを行う。
- 13.5 障害対応: 設定を従来方式へ戻し、所有セッションの状態を調査する。強制リセットには利用者の明示操作を必要とする。

## 14. テスト方針・計画

常駐端末の音声はスロット別に所有し、非選択スロットの回答を保留する。
選択変更は再生一時停止、PTT・明示停止は世代更新による取消として区別する。
画面の処理中状態は選択中の送信処理から、再生中状態はブラウザ実再生から決定する。
端末のフォーカス通知を入力ドラフトへ記録しない。CLIの実行自体と音声停止は別操作とする。
未回収の完了記録を次の入力で削除せず別に保持する。端末readの任意項目から再接続時に回収を再開する。
antigravityの失敗後に届く正常完了は、pendingの世代と台帳位置を照合して回収する。
正常完了が確認できないpendingは解除せず、新しい入力を混ぜない。
録音対応の事前確認に失敗した場合は既存の再生を止めない。
ブラウザ内で別スロットが処理していると判明している場合を除き、サーバーのthinkingを維持する。

- 14.1 種別と担当: 単体はコマンド列・モデル・重複排除、結合はtmuxとCLI、UATは利用者によるブラウザと音声確認。
- 14.2 環境・ツール: uv run pytest、Node既存画面テスト、隔離した試験tmuxセッション。実データや利用中のスロットを使わない。
- 14.3 完了基準: 要件ID別の受入観点を満たし、既存回帰試験成功、追加コードカバレッジ100%、品質ゲート4観点の確認。本書の搬送経路・保存上限・各CLI質問抑制が未確定な間は全体設計完了としない。
- 14.4 スケジュール: tmux制御の基盤 → ローカル1スロット → 3CLI → リモートARGOS → 切断・復帰・競合試験。

### Codex・agyへの拡張

Claudeの排他・所有権・端末搬送を共有し、providerごとの起動・フック正規化を追加する。
既存Claudeの台帳指紋は維持し、追加providerと指定された環境設定は指紋へ含める。
Codex/agyは初回の接続確認が終わってから入力可能とし、世代とnative IDを結び付けて完了を照合する。
Codexはturn_id、agyはstep_indexで重複を除外。ログ反映の遅延・不完全行・上限超過は成功として処理しない。
agyは名前付きworkspaceフックを導入し、専用のセッション環境変数がないCLIでは記録しない。
設定と外部仕様は[3CLIの試験手順](tmux-agents-trial.md)に記載する。恒久systemd連携は実装しない。

最初の試作はClaudeのローカル1スロットに限定する。具体的な設定名・手動試験・制限は[Claude試験手順](tmux-claude-trial.md)に記載した。フックはSessionStart・Stop・StopFailureのみを使い、確定本文を既存の応答経路へ返す。1行1MiB、台帳16MiBを記録上限とし、上限到達時は古い回答を黙って破棄せず試験を停止する。起動確認の上限は60秒、応答待ちはスロットのtmux_timeout_secondsで指定する。実際のpane IDを保存する。ブラウザ端末搬送と制限は[端末表示の仕様](tmux-console.md)で確定した。実Claude・Chromiumでの結合確認と、実機のマイク・スピーカーによる受入確認は区別する。
